1. Design

The system answers natural-language questions over the provided graphs by discovering a curated collection of graph tools, planning bounded tool calls, chaining intermediate graphs, and grounding structured answers in recorded tool results. It uses a LangGraph workflow and an OpenAI-compatible Gemini interface. The API key is read from LLM_API_KEY; it is not included in the submission.

  1. Curate and discover: An offline evaluator checks manifests, output contracts, deterministic repeated runs and independent semantic cases. It selects one implementation per official analytical tool and copies it unchanged into registry/tools/. At startup the orchestrator reads those manifests plus four instructor infrastructure tools. No student implementation is chosen by a query-specific runtime rule.
  2. Interpret: A structured query contract records the expected answer type, ordering, required facts and genuine user ambiguities. A dynamic graph catalogue supplies exact graph IDs, descriptions and attributes. Bounded, question-relevant node-label matches help resolve references without making them evidence for the final answer.
  3. Plan: Gemini proposes an acyclic dependency graph of at most five tool calls. Tool names come from discovered manifests; literal graph IDs and dependency pointers are validated before execution. A plan may instead declare clarification_needed or unsupported.
  4. Execute and assess: Ready steps run sequentially against one GraphStore. JSON Pointer bindings pass node IDs or a tool's /result_graph_id into later steps. Successful outputs are checked against the tool contract. A separate evidence assessment requests more analysis if required facts are missing; failures trigger bounded replanning.
  5. Finalize and recover: The final structured value must match the query contract and cite real output paths. JSONL traces retain LLM calls, tool arguments/results and final answers. A SQLite checkpoint, response cache, provider retry and tool replay support interrupted runs.

2. Registry selection

The local curation report evaluated 186 candidate implementations and selected one implementation for each of the 33 analytical tools; the four infrastructure tools remain separate. Passing a schema check alone was not sufficient: selected tools also needed the expected behavior, bounded output and useful chaining semantics. Published registry source files were not edited.

4. Failure analysis

  • q17 — evidence scope misjudged: Degree centrality on an instructor ego subgraph ranked m1 first and m2 next. The question asked for the most connected friend, excluding m1. The assessor incorrectly called that derived-subgraph ranking a global ranking and replanning exhausted its limit. A later run still lacked a matching successful terminal answer.
  • q22 — incomplete multi-step plan: Triangle counting in Javert's immediate circle requires resolving Javert, constructing an ego subgraph, then running a motif-count tool. A prior plan embedded arguments in tool-name strings; a later attempt called clustering tools instead and hit the replan limit. No supported terminal number was obtained.
  • q21 — wrong graph for the calculation: Betweenness was calculated on all 77 lesmis characters, making Myriel (c63) rank second globally. The workflow then built Valjean's neighbour graph without recalculating betweenness there. Instead it should calculate betweenness on Valjean's 37-node ego graph (including Valjean), then exclude Valjean only when choosing the answer. That calculation ranks Javert (c40) next, at 0.062634.
  • q26 — ambiguity pursued as a computation: “How close” could mean hops, shared chapters or neighbourhood similarity. The later run tried weighted shortest-path steps and failed instead of asking for clarification. Shared-chapter counts describe link strength, not distance; the earlier clarification is intentionally not used.
